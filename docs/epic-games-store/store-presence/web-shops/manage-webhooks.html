Manage Webhooks

Create and manage your web shop's webhook.

27 mins to read

Webhooks are HTTP callbacks you must create in order to use a web shop. They connect your web shop on the Epic Games Store to your product’s backend every time a web shop item is purchased or refunded on your web shop. The communication between your webhook and your product is sandbox agnostic. You manage webhooks on the Web Shop page of the Developer Portal.

There are a few requirements for webhooks, because your webhook sends and receives confidential information between your product’s backend and the Epic Games Store. You must:

  • Generate and maintain at least one webhook secret. You use this secret to securely communicate with the webhook API.
  • Sign and verify the values timestamp and signature for every webhook call.
  • Perform a validation test (see Run a Validation Test on your Webhook on this page), for every secret you generate.

Generate a Webhook Secret

In the Developer Portal, use the Webhook Management page to generate a webhook secret. You can have a maximum of two secrets.

To generate a webhook secret:

  1. In the Developer Portal, go to the Web Shop page. To do this:

    • a. Sign in to the Developer Portal (dev.epicgames.com/portal).

    • b. Select the correct organization for your product.

      (To check, see Organization at the top of the left navigation. To change organization, click Organization and follow the on-screen instructions.)

    • c. In the left navigation, under Your products, click the name of your product.

    • d. In the left navigation, click Epic Games Store > Web Shop.

  2. Find the Webhook management section and click Edit.
  3. In the Webhook Management panel, click Generate secret.
  4. Select a secret expiry date from the following options:
    • No expiry date: This secret never expires and can always be used.
    • Schedule an expiration date: This secret expires on the selected date. After the secret expires, every call that uses this secret will fail.
  5. Click Generate.
  6. On the Secret details page, you are shown the following information:
    • ID: The unique identifier for the secret, you use this id to communicate with the webhook.
    • Expiry date: If you selected a scheduled expiry date at step 4, it is displayed in this field. If you didn’t select an expiry date, "No expiry date" is displayed instead.
    • Secret: You must use this secret every time you communicate with the webhook. This is the only time the secret will be shown, so be sure to copy the secret to a secure location.
  7. Click Close.

Delete a Webhook Secret

In the Developer Portal, use the Webhook Management page to delete a webhook secret. You might want to delete a secret when the secret is no longer in use, or to do a secret rotation. For more information, see Rotate a Webhook Secret on this page. When you delete a secret, every call that uses this secret will now fail.

To delete a webhook secret:

  1. In the Developer Portal, go to the Web Shop page. To do this:

    • a. Sign in to the Developer Portal (dev.epicgames.com/portal).

    • b. Select the correct organization for your product.

      (To check, see Organization at the top of the left navigation. To change organization, click Organization and follow the on-screen instructions.)

    • c. In the left navigation, under Your products, click the name of your product.

    • d. In the left navigation, click Epic Games Store > Web Shop.

  2. Find the Webhook management section and click Edit.
  3. In the Webhook Management panel, click Secrets.
  4. Find the secret you want to delete and click Delete Secret.
  5. Click Yes, delete.
  6. Click Close.

Rotate a Webhook Secret

To maintain a secure environment for your webhook and webhook secrets, we recommend doing a periodic webhook secret rotation. You can have a maximum of two secrets. A rotation is done in two separate places:

  • On the Web Shop page in the Developer Portal.
  • In your app that sends and receives information from the webhook API.

To rotate a webhook secret:

  1. Generate a secret. See Generate a Webhook Secret on this page.
  2. In your app, configure your webhook to use the new secret.
  3. When your previous secret is no longer in use in your deployment, delete the previous secret. See Delete a Webhook Secret on this page.

Run a Validation Test on your Webhook

In the Developer Portal, you can test if your webhook is working using the validation test feature on the Web Shop page.

To run a validation test on your webhook:

  1. In the Developer Portal, go to the Web Shop page. To do this:

    • a. Sign in to the Developer Portal (dev.epicgames.com/portal).

    • b. Select the correct organization for your product.

      (To check, see Organization at the top of the left navigation. To change organization, click Organization and follow the on-screen instructions.)

    • c. In the left navigation, under Your products, click the name of your product.

    • d. In the left navigation, click Epic Games Store > Web Shop.

  2. Find the Webhook management section and click Edit.
  3. In the Webhook Management panel, enter the following information:
    • Endpoint URL: The URL of the endpoint that will send and receive information for the webhook. You must follow these requirements:
      • Use the HTTPS protocol for your endpoint URL.
      • Do not use query parameters or fragment IDs.
      • Use a DNS for authority purposes. Do not use a raw IP address.
      • Do not include authentication credentials in the authority section of the URL.
      • Do not use 3xx redirect response codes.
    • Test fields: The fields you will send to your endpoint from the web shop when you test the webhook. Use the following guidance to help you enter the details:
      • Namespace: Refers to the name of the sandbox.
      • Web shop item ID: The unique identifier for the web shop item. (Documentation: Manage Web Shop Items > Add Web Shop Item Details.)
      • External Player ID: The player ID you want to run the validation test. (Documentation: Manage Web Shops > Edit web shop details.)
  4. Click Run validation test.
    • The Developer Portal displays an alert indicating if your test was successful or not. If the validation failed, you can download the associated har file to learn more. For more support, create a private discussion on the support website: eoshelp.epicgames.com.
  5. Click Validate and save.

Webhook API Response Types

When you call the webhook API, you receive a response. The following are the different types of responses you might receive. Use this guidance to help you code your product’s backend:

  • response-v1-acknowledge: The call was sent and received successfully.
  • response-v1-player-id-verification: It is up to you to perform the appropriate playerId verification. Failure to verify a playerId results in a purchase restriction. Some reasons to restrict a purchase include (but are not limited to): player age, account not in good standing, or geo-location restriction for this playerId.
  • response-v1-fulfill: A fulfillment event is used to fulfill a purchase. You must respond with a properly signed 200 response of type ResponseV1Fulfill to indicate success.
  • response-v1-clawback: A clawback response is the final state of a clawback event. Under some circumstances (such as intermittence in your webhook or network), you might receive a clawback event first. For any fulfillment events that arrive after a clawback event, you must do the following:
    • You must acknowledge the fulfillment event with a properly-signed 200 response.
    • You must not grant the purchase to the player.
    The conditions above are protections in case you receive additional fulfillment events after a clawback event. Event ordering is not guaranteed, you must ensure idempotency in your fulfillment logic to prevent inconsistent states. (Documentation: Ecom Web APIs.)

Webhook API FAQ

What is the intended use case for the namespace in the fulfillment and clawback calls?

You need to use this namespace if you want to access the Dev and Stage sandboxes. The namespace is used in conjunction with the Epic Online Services (EOS) SDK Ecom API. If you don’t plan on using the Ecom API, you can ignore the namespace field.

For more information, see the following documentation:

  • Developer Portal > Product Management > Sandboxes and Deployments
  • EOS SDK API Reference > Catalog Offer

What is the expected behavior when a playerId or offerId are invalid in a fulfill or clawback event?

If the playerId or offerId is invalid, the webhook API returns the following messages:

  • In the fulfill or clawback event, the API returns 400 - Bad Request.
  • In the playerId verification event, the API returns 200 - OK, with the DENIED status.

Do I need to confirm that the playerId and offerId match any existing records in a clawback event (or an out-of-order fulfillment event)? What is the expected behavior if the IDs don't match?

You don’t have to account for incorrect playerId or offerId values in fulfillment and clawback events. The Webhook API records whichever value comes in first. Fulfillment and clawback events share the same fulfillment ID.

You cannot rely on receiving a fulfillment event before you handle a clawback event. Our recommendation is that you record all events and do whatever is appropriate for your business rules for handling a clawback event. When you receive a clawback event for a given fulfillment ID, you must check if you have granted the purchase with a fulfillment event with the same fulfillment ID. There are two different workflows on what to do next, depending if you have received a fulfillment event:

  • If you have a matching fulfillment event, follow your clawback business model.
  • If you don’t have a matching fulfillment event, you must record the clawback. Then, for any matching fulfillment event, do not grant the web shop item. As an example, you might use a transactional database to lock the fulfillment ID to ensure consistency. This prevents race conditions between clawback and fulfillment events when you use distributed concurrent event handling.

During signature verification, what is the expected behavior if multiple signatures are received, but one of them is malformed (for example "S4428=2dba925,malformed-signature")?

The webhook API returns 401 - Unauthorized, even if your other signatures are valid.

Webhook Signing Code Samples

This section provides basic examples of how to set up and configure a Webhook receiver API. It covers example functions for signing and verifying timestamp and signature, and provides a basic API scaffold to help you get started.

This section includes code samples for the following languages:

  • Typescript/NodeJS/Express
  • Java/Spring Boot
  • Python/Django

Note: Each of the code samples uses an example secret with the same format as a real secret. Replace this example secret with your own secret, and store and use your secret safely.

Sign and Verify the Timestamp and Signature

Each language uses the following pattern for signing and verification:

  • The sign function outputs an X-Signature header value in the format of {id}={signature}.
  • The verifySignature function computes the expected signature and compares the expected signature with the signature using a timing safe method. It returns a boolean value indicating if the signature is valid.
  • The verifyTimestamp function verifies that the timestamp is + or - 5 minutes from the current system time. It returns a boolean value indicating if the timestamp is valid.

Note:

  • When you sign or verify the body, make sure to compute signatures from the raw body. This is because JSON serialization and deserialization can modify whitespaces and property orders.
  • When multiple secrets are configured (for example, during secret rotation), you might receive multiple signatures in the header. When multiple signatures are present, verify that at least one is valid with the locally-configured secret. This allows for secret rotation without downtime.

The following examples show how to implement the sign and verify functions. You need to use a webhook ID and webhook secret from the Developer Portal (for information, see Generate a Webhook Secret on this page).

Use createHmac() to create a hmac Object.export function sign(timestamp: string, body: string | Buffer): string {  const data = timestamp + body;  const hmac = crypto.createHmac('sha256', SECRET);  const signature = hmac.update(data).digest('hex');  return `${SECRET_ID}=${signature}`;} // verifySignature() verifies that signature is valid. The function returns true if the constant expectedSignature is equal to signature.export function verifySignature(  signature: string,  timestamp: string,  body: string | Buffer): boolean {  const expectedSignature = sign(timestamp, body);   const [signatureId, signatureValue] = signature.split('=');  const [expectedId, expectedValue] = expectedSignature.split('=');   // verify the id is the same  if (signatureId !== expectedId) {    return false;  }   // verify the signature values are not empty  if (!signatureValue || !expectedValue) {    return false;  }   // compares using timingSafeEqual to prevent timing attacks  const signatureBuffer = Buffer.from(signatureValue, 'hex');  const expectedBuffer = Buffer.from(expectedValue, 'hex');   // timingSafeEqual requires buffers to be the same length  if (    signatureBuffer.length === 0 ||    signatureBuffer.length !== expectedBuffer.length  ) {    return false;  }   return crypto.timingSafeEqual(signatureBuffer, expectedBuffer);} // verifyTimestamp() verifies that the timestamp has less than a 5 minute difference from your system time.export function verifyTimestamp(timestamp: string): boolean {  const now = Date.now();  const date = Date.parse(timestamp);   // + or - 5 minutes (in ms)  const min = now - 300_000;  const max = now + 300_000;   return date >= min && date <= max;}

package com.example.webhook; import org.springframework.stereotype.Service; import javax.crypto.Mac;import javax.crypto.spec.SecretKeySpec;import java.nio.charset.StandardCharsets;import java.security.InvalidKeyException;import java.security.NoSuchAlgorithmException;import java.time.Duration;import java.time.Clock;import java.time.Instant;import java.time.format.DateTimeParseException; @Servicepublic class SigningService {    private static final String ALGORITHM = "HmacSHA256";    private static final String SECRET_ID = "S7663";    private static final String SECRET = "KXJaWQDXVrIRyB6OV5znTn2EJ6ugN/Y1tdWOx48g6jQ=";    private final Clock clock;     public SigningService(Clock clock) {        this.clock = clock;    }     public boolean verifySignature(String idAndSignature, String timestamp, byte[] data) {        try {             String[] parts = idAndSignature.split("=", 2);            if (parts.length != 2) {                return false;            }            if (!parts[0].equals(SECRET_ID)) {                return false;            }            Instant signedAt = Instant.parse(timestamp);            verifyTimestamp(signedAt);            String computedIdAndSignature = sign(signedAt, data);            return idAndSignature.equals(computedIdAndSignature);        } catch (DateTimeParseException e) {            throw new RuntimeException("Failed to parse webhook timestamp", e);        }    }     public boolean verifyTimestamp(Instant signedAt) {        Instant lowerBoundary = Instant.now(clock).minus(Duration.ofMinutes(5L));        Instant upperBoundary = Instant.now(clock).plus(Duration.ofMinutes(5L));         return signedAt.isAfter(lowerBoundary) && signedAt.isBefore(upperBoundary);    }     public String sign(Instant timestamp, byte[] data) {        try {            SecretKeySpec secretKeySpec = new SecretKeySpec(SECRET.getBytes(), ALGORITHM);            Mac mac = Mac.getInstance(ALGORITHM);            mac.init(secretKeySpec);            byte[] combinedBytes = combine(timestamp, data);            return SECRET_ID + "=" + bytesToHex(mac.doFinal(combinedBytes));        } catch (NoSuchAlgorithmException | InvalidKeyException | IllegalArgumentException e) {            throw new RuntimeException("Failed to calculate HMAC", e);        }    }     private static byte[] combine(Instant timestamp, byte[] data) {        byte[] timeStampBytes = timestamp.toString().getBytes(StandardCharsets.UTF_8);        byte[] combined = new byte[timeStampBytes.length + data.length];        System.arraycopy(timeStampBytes, 0, combined, 0, timeStampBytes.length);        System.arraycopy(data, 0, combined, timeStampBytes.length, data.length);        return combined;    }     private static String bytesToHex(byte[] bytes) {        StringBuilder hexStringBuilder = new StringBuilder();        for (byte b : bytes) {            hexStringBuilder.append(String.format("%02x", b));        }        return hexStringBuilder.toString();    }}

SigningService.java
package com.example.webhook; import org.springframework.stereotype.Service; import javax.crypto.Mac;import javax.crypto.spec.SecretKeySpec;import java.nio.charset.StandardCharsets;import java.security.InvalidKeyException;import java.security.NoSuchAlgorithmException;import java.time.Duration;import java.time.Clock;import java.time.Instant;import java.time.format.DateTimeParseException; @Servicepublic class SigningService {    private static final String ALGORITHM = "HmacSHA256";    private static final String SECRET_ID = "S7663";    private static final String SECRET = "KXJaWQDXVrIRyB6OV5znTn2EJ6ugN/Y1tdWOx48g6jQ=";    private final Clock clock;     public SigningService(Clock clock) {        this.clock = clock;    }     public boolean verifySignature(String idAndSignature, String timestamp, byte[] data) {        try {             String[] parts = idAndSignature.split("=", 2);            if (parts.length != 2) {                return false;            }            if (!parts[0].equals(SECRET_ID)) {                return false;            }            Instant signedAt = Instant.parse(timestamp);            verifyTimestamp(signedAt);            String computedIdAndSignature = sign(signedAt, data);            return idAndSignature.equals(computedIdAndSignature);        } catch (DateTimeParseException e) {            throw new RuntimeException("Failed to parse webhook timestamp", e);        }    }     public boolean verifyTimestamp(Instant signedAt) {        Instant lowerBoundary = Instant.now(clock).minus(Duration.ofMinutes(5L));        Instant upperBoundary = Instant.now(clock).plus(Duration.ofMinutes(5L));         return signedAt.isAfter(lowerBoundary) && signedAt.isBefore(upperBoundary);    }     public String sign(Instant timestamp, byte[] data) {        try {            SecretKeySpec secretKeySpec = new SecretKeySpec(SECRET.getBytes(), ALGORITHM);            Mac mac = Mac.getInstance(ALGORITHM);            mac.init(secretKeySpec);            byte[] combinedBytes = combine(timestamp, data);            return SECRET_ID + "=" + bytesToHex(mac.doFinal(combinedBytes));        } catch (NoSuchAlgorithmException | InvalidKeyException | IllegalArgumentException e) {            throw new RuntimeException("Failed to calculate HMAC", e);        }    }     private static byte[] combine(Instant timestamp, byte[] data) {        byte[] timeStampBytes = timestamp.toString().getBytes(StandardCharsets.UTF_8);        byte[] combined = new byte[timeStampBytes.length + data.length];        System.arraycopy(timeStampBytes, 0, combined, 0, timeStampBytes.length);        System.arraycopy(data, 0, combined, timeStampBytes.length, data.length);        return combined;    }     private static String bytesToHex(byte[] bytes) {        StringBuilder hexStringBuilder = new StringBuilder();        for (byte b : bytes) {            hexStringBuilder.append(String.format("%02x", b));        }        return hexStringBuilder.toString();    }}

import hmacimport hashlibimport base64from datetime import datetime, timedelta # Example secret id and value# In real app, these values are stored in your database.# Python requires bytes for HMAC, so we convert from base64 to bytes.SECRET_ID = 'S7663'  # Identifier for the secret keySECRET = b'KXJaWQDXVrIRyB6OV5znTn2EJ6ugN/Y1tdWOx48g6jQ='  # Base64-encoded secret # Calculates signature from timestamp and bodydef sign(timestamp: str, body: str | bytes) -> str:    # Convert to bytes if string    if isinstance(body, str):        body = body.encode('utf-8')        data = timestamp.encode('utf-8') + body # converts to bytes. ex: b'12345'     # Generates SHA-256 HMAC (a valid hexadecimal string) for given data using secret key    signature = hmac.new(SECRET, data, hashlib.sha256).hexdigest()        return f"{SECRET_ID}={signature}" # Verifies that signature is validdef verify_signature(signature: str, timestamp: str, body: str | bytes) -> bool:    expected_signature = sign(timestamp, body)    try:        signature_id, signature_value = signature.split('=')        expected_id, expected_value = expected_signature.split('=')    except ValueError:        return False     # Verify the id is the same    if signature_id != expected_id:        return False     # Verify the signature values are not empty    if not signature_value or not expected_value:        return False     # Compares using hmac.compare_digest to prevent timing attacks    try:        signature_bytes = bytes.fromhex(signature_value)        expected_bytes = bytes.fromhex(expected_value)    except ValueError:        # Invalid hex string        return False      # compare_digest requires buffers to be the same length    if len(signature_bytes) == 0 or len(signature_bytes) != len(expected_bytes):        return False     return hmac.compare_digest(signature_bytes, expected_bytes) # Verifies that the timestamp is current with system timedef verify_timestamp(timestamp: str) -> bool:    try:        # Parse the timestamp string into a datetime object        ts = datetime.fromisoformat(timestamp.rstrip('Z'))         now = datetime.utcnow()        window = timedelta(minutes=5)         return now - window <= ts <= now + window    except Exception:        return False
